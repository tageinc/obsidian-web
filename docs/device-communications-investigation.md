## Response and compatibility contract

- Successful software lookup remains HTTP 200 with a string `version`. Successful downloads retain their bytes and attachment behavior. Existing ordering is preserved (latest creation for versionless downloads, descending version for prefix lookup).
- Missing firmware/configuration version lookup returns HTTP 404 and `{"version":"0","error":"no_matching_version"}`. The old field/type is retained for tolerant clients. A real version `0` remains HTTP 200. Missing records, omitted prefixes, null paths, or absent files return HTTP 404 for downloads. Clients must check HTTP status before interpreting a version. Firmware source was unavailable; this change is not yet certified against deployed firmware.
- Software warnings contain kind, selector, reason, and a hash of the selector. They do not include URLs, query strings, payloads, storage paths, or credentials.
- Telemetry retains the form/JSON envelope: `serial_no` is a nonempty string of at most 255 characters; `data` is a JSON **object encoded as a string**, at most 16,384 characters. Success remains `{"msg":"success"}`. Existing unregistered-device and unsupported-hardware responses are retained.
- Hardware 1 fields: `ps1`, `ps2`, `ps_avg`, `pds`, `motor_speed`, `temp`, `cts`, `state`. Hardware 2 fields: `v_batt`, `i_batt`, `v_sol`, `i_sol`, `i_inv`, `temp`. Partial reports, finite numeric strings, zero values, nullable missing fields, and extra extension fields are supported. At least one recognized non-null value is required. Supplied numeric fields must be finite numbers/numeric strings; `cts` must be an integer; `state` must be a nonblank string of at most 255 bytes. Invalid envelopes, JSON, known-field types, and unknown-only/null-only reports return JSON HTTP 422 without a telemetry write.
- `/api/log` adds a per-serial limiter (`DEVICE_TELEMETRY_PER_MINUTE`, default 1000), in addition to the API per-IP 1000/minute limiter. HTTP 429 includes `Retry-After`. A high default avoids inventing a lower report cadence without device evidence. Shared NAT/proxy deployments can still share the IP limit; verify trusted proxies and actual traffic before tuning. Serial numbers are not authentication. Mandatory new device credentials would break existing firmware, so authentication was not introduced.
- `DEVICE_TELEMETRY_FRESHNESS_SECONDS` defaults to 600, matching the previous energy-monitor window. Receipt `created_at` must be strictly newer than the cutoff and not in the future. Missing/stale records classify supported hardware as offline before applying alarm conditions; fresh solar state is preserved, with `online` for a partial report without state. Unsupported hardware is `unknown`. Status evaluation uses only the registered hardware's table.
- The hourly scheduler can delay persisted offline status until the next run (up to approximately 70 minutes after the last receipt at the default threshold). Historical telemetry endpoints still return historical measurements. No schedule or UI contract is changed here.

## Read-only production evidence collection

Use the incident time range, UTC, with a known-good comparison interval. Record environment and deployed commit for each result; redact identifiers and secrets in shared evidence. Do not invoke `device:check-status`, scheduler commands, telemetry POSTs, firmware upload routes, or migrations for diagnosis: these can write data or send notifications.

1. Obtain the inventory of every deployed application/worker environment and its database/cache connection. Review deployment timestamp, configuration-cache timestamp, scheduler history, proxy/CDN errors, TLS/DNS and upstream health. Do not dump environment files or credentials.
2. On each environment, with a read-only DB account and this code available for review, run `php artisan device:audit-telemetry`. This command only queries schema metadata; it never creates tables/indexes or changes records. Exit 0 means required columns and an index whose **first** column is `serial_no` exist on both tables. Exit 1 means missing requirements, connection failure, or unsupported metadata driver. MySQL and SQLite are supported. It also reports whether `(serial_no, created_at)` leads an index, recommended for latest-record queries. Preserve output and exit code. Do not interpret unavailable as absent.
3. Have the database operator capture `SHOW COLUMNS FROM solar_tracker_logs`, `SHOW COLUMNS FROM energy_monitor_logs`, and `SHOW INDEX` for both (apply configured table prefix). Compare field types, nullability, timestamp handling, and lengths with valid captured device reports and model fields. Numeric columns must accommodate the actual firmware values; `state`/`serial_no` must accommodate production lengths. The automated audit checks presence, not type compatibility. Do not invent a migration until existing definitions and rollout history are known.
4. Aggregate existing access logs by minute, normalized route, status and environment for `/api/log`, `/api/firmware-version/*`, `/api/config-version/*`, software downloads and remote-control reads. Look for 429 bursts near 1000 combined API requests/minute, 500/404 spikes, ingestion latency, retries and recovery at bucket resets. Never export complete URLs, tokens, or telemetry bodies. Check whether all app instances share a cache bucket.
5. Correlate existing application error categories (missing-record dereferences, missing-table/column SQLSTATE, insert/type errors, connection failures, disk/file failures) with access logs. New code logs `device.software_unavailable` and `device.telemetry_rejected`; these events cannot explain historical traffic until deployed with separate approval. Avoid exporting raw exception text that contains SQL/bindings.
6. After index verification, inspect latest `created_at` for a small bound sample of affected and unaffected registered serials in their applicable table using parameterized SELECTs, `WHERE serial_no = ? ORDER BY created_at DESC LIMIT 1`. Compare receipt age with access-log POST success times, hardware ID and displayed status. Avoid fleet-wide scans while investigating an overloaded database.
7. Read matching prefix/version/path metadata for the affected device families with bounded SELECTs. Verify referenced files using read-only storage metadata and compare with the deployed firmware's expected prefix/version semantics. Do not publish firmware, change a version, set a device state, or trigger an update during diagnosis.
8. Bench-test each deployed firmware family with captured valid telemetry and 200, 404, 422, 429 and retry behavior. Confirm actual payload sizes/types, cadence, string version handling, and that 404 cannot trigger an unintended downgrade. This is a release gate, not a claim already verified by server tests.
